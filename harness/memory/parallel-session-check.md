사용자는 병렬 세션을 돌리므로(→ [[parallel-work-and-models]]) 운영 DB·서버·기기를 건드리기 전에 **다른 세션이 지금 뭘 하는지 확인하고, 안 겹치는 것부터** 하라고 요구한다 (2026-09-20).

**Why:** git 상태만 보면 충돌을 못 본다. 09-20 프로젝트 E에서 다른 세션은 커밋도 워크트리 변경도 0이었는데 실제로는 폰으로 푸시 알림을 실측 중이었고, 내 마이그레이션이 걷는 트리거가 정확히 그 발송 경로였다. 파일이 아니라 **운영 자원**이 겹친 것이다.

**How to apply:**
1. `ListAgents` → busy 세션 확인. `mcp__ccd_session_mgmt__list_sessions`로 cwd·branch.
2. **`mcp__ccd_session_mgmt__list_events`로 전사를 읽는다** — 여기서만 «지금 기기로 뭘 하는지»가 보인다. limit 25는 도구 호출만 나와 쓸모없다. **120쯤 줘야 assistant 텍스트가 나온다.**
3. 유휴 감지는 세션의 `isRunning`이 아니라(대화형 세션은 끝나도 살아 있다) **전사 jsonl의 mtime**으로 본다. `stat -f %m`이 4분 이상 안 바뀌면 유휴. Monitor에 until 루프로 걸면 알림이 온다. **함정 — project dir는 워크트리마다 따로다.** 메인 프로젝트 폴더의 `*.jsonl`만 `ls`하면 옛것만 나와 «아무도 없다»로 오판한다(09-20 실제로 그랬다). 전체를 훑을 것: `find ~/.claude/projects -name '*.jsonl' -mtime -1`.
4. **누가 무엇을 했는지 가장 빠른 단서는 메모리 파일이다.** 세션 중에 mtime이 바뀌면 그쪽이 방금 뭔가 끝낸 것이고, frontmatter의 `originSessionId`가 그 세션의 jsonl 이름과 같다. `gh issue list --limit`의 «just now»도 같은 신호다 — 09-20에 내가 «막혀 있다»로 이슈를 내는 사이 옆 세션이 그걸 풀어서, **낸 지 2분 만에 전제가 틀린 이슈**가 됐다. 운영 자원뿐 아니라 **이슈 본문의 사실**도 겹친다. 내기 전에 한 번 더 볼 것.
5. 겹치면 **코드·문서·PR은 먼저 머지하고 운영 반영만 미룬다.** 마이그레이션을 일찍 머지하면 번호 충돌 위험도 줄어든다.
6. 상대가 «사용자 입력 대기»로 멈춘 것이면 «끝나기»를 기다리면 안 온다 — 겹치지 않는 일부터 하고, 그 세션의 질문은 감독 세션이 폰 알림으로 넘긴다([[supervisor-session]]).

바쁜 세션에 SendMessage로 끼어들지 말 것 — 그쪽 턴에 주입돼 실측을 망친다.

## 설정·하네스 변경은 세션들이 조용할 때 (11-09)

사용자: «설정 관련된 부분이니까 세션들이 모두 조용해지면 그때부터 일 시작… 백그라운드로 진행 상황 확인하고 있다가 끝나면 시작». 다른 세션이 기기 시험 중일 때 플러그인·훅·권한 같은 설정이 바뀌면 그 세션을 흔들 수 있다.
- 사용자 범위 설정·훅·플러그인 변경은 다른 세션이 쉴 때 한다. 기다림은 에이전트 대신 토큰이 안 드는 백그라운드 셸 감시로 — `~/.claude/projects/**/*.jsonl`(자기 세션 제외)이 30분 동안 안 바뀌고 빌드 프로세스가 없으면 끝나며 세션을 깨운다 → 깨어나면 list_sessions로 isRunning을 한 번 더 본다. 11-09 첫 사용: 01:47 감시 시작 → 02:31 조용.
